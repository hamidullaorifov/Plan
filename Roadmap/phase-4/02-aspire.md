# 2. Aspire: Local Orchestration and Service Defaults

> Phase 4 · Week 2 · [← Phase index](README.md)

**Why this matters:** A realistic .NET system locally means an API, a worker, PostgreSQL, Redis, a broker and maybe a front end. Starting all of that by hand, with consistent connection strings and visible telemetry, is painful. **Aspire** (formerly ".NET Aspire") models the whole system in code, runs it with one command and shows logs, traces and metrics in one dashboard. It's quickly becoming the default local-development experience for .NET teams.

---

## 2.1 What Aspire is and isn't

| Aspire **is** | Aspire **isn't** |
|---|---|
| an **AppHost**: code that describes your services, databases, caches and their relationships | a production runtime or a cloud provider |
| a local orchestrator: `aspire run` starts everything in the right order | a replacement for ASP.NET Core or your frameworks |
| a **dashboard**: logs, traces, metrics and resource state in one place | required in production (your app runs without it) |
| **service defaults**: OpenTelemetry, health checks, service discovery and resilience in one call | magic. It's regular code you can read |
| a deployment model you can publish to Azure Container Apps, Kubernetes and Docker Compose | |

## 2.2 The AppHost

```csharp
// AppHost/AppHost.cs
var builder = DistributedApplication.CreateBuilder(args);

var postgres = builder.AddPostgres("postgres")
    .WithDataVolume()                          // keep data between runs
    .WithPgAdmin();                            // optional admin UI
var shopDb = postgres.AddDatabase("shop");

var redis = builder.AddRedis("redis");
var rabbit = builder.AddRabbitMQ("messaging").WithManagementPlugin();

var api = builder.AddProject<Projects.Shop_Api>("api")
    .WithReference(shopDb).WaitFor(shopDb)     // injects ConnectionStrings__shop and waits until healthy
    .WithReference(redis).WaitFor(redis)
    .WithReference(rabbit).WaitFor(rabbit)
    .WithExternalHttpEndpoints();

builder.AddProject<Projects.Shop_Worker>("worker")
    .WithReference(shopDb).WaitFor(shopDb)
    .WithReference(rabbit).WaitFor(rabbit);

builder.Build().Run();
```

What happens when you run it:

1. Containers start for PostgreSQL, Redis and RabbitMQ (with generated passwords stored as user secrets).
2. **Connection information is injected** into each project as configuration (`ConnectionStrings__shop`, `ConnectionStrings__redis` and so on).
3. `WaitFor` delays a project's start until its dependency reports healthy.
4. The dashboard opens with every resource, its console logs, structured logs, traces and metrics.

```powershell
# Install the CLI and templates (check aspire.dev for the current install command)
aspire new            # interactive template selection
aspire run            # run the AppHost and open the dashboard
```

## 2.3 Service defaults

The `ServiceDefaults` project (generated by the templates) contains one extension method that every service calls:

```csharp
// Shop.Api/Program.cs
var builder = WebApplication.CreateBuilder(args);
builder.AddServiceDefaults();          // OpenTelemetry, health checks, service discovery, HttpClient resilience

builder.AddNpgsqlDbContext<ShopDbContext>("shop");   // Aspire client integration: reads ConnectionStrings:shop
builder.AddRedisClient("redis");

var app = builder.Build();
app.MapDefaultEndpoints();             // /health and /alive (in Development by default)
app.Run();
```

**What `AddServiceDefaults` typically configures** (it's generated code in *your* repo, so read it and adjust it):

| Area | Configuration |
|---|---|
| OpenTelemetry | logging, metrics (ASP.NET Core, HttpClient, runtime) and tracing, plus the OTLP exporter when `OTEL_EXPORTER_OTLP_ENDPOINT` is set |
| Health checks | a default `self` liveness check; `MapDefaultEndpoints` maps the endpoints |
| Service discovery | `http://api` and `https+http://api` resolve to the right address, locally and when deployed |
| HttpClient defaults | `AddStandardResilienceHandler()` and service discovery on every `HttpClient` |

> Health endpoints are mapped **only in Development** by default in the template, because exposing health details publicly can leak information. Decide deliberately how to expose them in production (internal port, auth, or Kubernetes probes only).

## 2.4 Client integrations vs hosting integrations

| | Hosting integration (AppHost) | Client integration (your service) |
|---|---|---|
| Package | `Aspire.Hosting.PostgreSQL` | `Aspire.Npgsql.EntityFrameworkCore.PostgreSQL` |
| Purpose | **runs** the resource (a container locally, a cloud resource when deployed) | **connects** to it, with health checks, telemetry and retries configured |
| API | `builder.AddPostgres("postgres")` | `builder.AddNpgsqlDbContext<T>("shop")` |

Client integrations are optional. You can keep `AddDbContext` with `GetConnectionString("shop")`. They give you a consistent setup: health checks, tracing and sensible defaults.

## 2.5 Service discovery between projects

```csharp
// AppHost
var catalog = builder.AddProject<Projects.Catalog_Api>("catalog");
builder.AddProject<Projects.Shop_Api>("api").WithReference(catalog);

// Shop.Api: the logical name "catalog" resolves to the real endpoint
builder.Services.AddHttpClient<CatalogClient>(c => c.BaseAddress = new Uri("https+http://catalog"));
```

`https+http://` means "prefer HTTPS, fall back to HTTP". The same code works locally and in Azure Container Apps or Kubernetes, because the deployment sets the equivalent configuration.

## 2.6 Testing with Aspire

`Aspire.Hosting.Testing` starts the **whole AppHost** in a test, which gives you real end-to-end tests:

```csharp
public class ApiSmokeTests
{
    [Fact]
    public async Task Health_endpoint_returns_ok()
    {
        var ct = TestContext.Current.CancellationToken;
        var appHost = await DistributedApplicationTestingBuilder.CreateAsync<Projects.AppHost>(ct);
        await using var app = await appHost.BuildAsync(ct);
        await app.StartAsync(ct);

        using var http = app.CreateHttpClient("api");
        await app.ResourceNotifications.WaitForResourceHealthyAsync("api", ct);

        var response = await http.GetAsync("/health", ct);
        Assert.Equal(HttpStatusCode.OK, response.StatusCode);
    }
}
```

Use these for a handful of **smoke and end-to-end tests**. Keep most integration tests on `WebApplicationFactory` + Testcontainers (Phase 2), because they're faster and more focused.

## 2.7 From AppHost to deployment

The AppHost is an **application model**: a description of resources and their relationships. Deployment tooling can translate it:

| Target | How (check aspire.dev for the current commands) |
|---|---|
| **Azure Container Apps** | `azd up` (Azure Developer CLI) or `aspire deploy`, which provisions Container Apps, a registry, managed identity and the resources you modeled |
| **Kubernetes** | publish to Kubernetes manifests or Helm, then apply with your usual tooling |
| **Docker Compose** | publish a Compose file for simple VM hosting |

> **Production thinking:** local containers become **managed services** in production (Azure Database for PostgreSQL, Azure Cache for Redis, Service Bus). The AppHost can express that, for example with `AddAzurePostgresFlexibleServer(...)` and `.RunAsContainer()` for local runs. Review the generated infrastructure: networking, SKUs, backups and identity are *your* responsibility.

## Interview questions

<details><summary><b>1. What problem does Aspire solve?</b></summary>

It describes a distributed app's resources and relationships in code (the AppHost), runs them locally with correct wiring (connection strings, service discovery, start order), and gives one dashboard for logs, traces and metrics. The same model can be used for deployment.
</details>

<details><summary><b>2. Is Aspire needed in production?</b></summary>

No. The services are ordinary .NET apps. Service defaults (OpenTelemetry, health checks, resilience) are regular code that runs anywhere. The AppHost is used for local orchestration and as an input to deployment tooling.
</details>

<details><summary><b>3. What's the difference between hosting and client integrations?</b></summary>

Hosting integrations (used in the AppHost) run or provision a resource. Client integrations (used in services) configure the connection to it, including health checks, telemetry and retries.
</details>
